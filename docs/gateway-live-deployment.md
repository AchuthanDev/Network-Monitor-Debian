## nftables Design

The generated table is project-owned:

```text
table inet network_monitor
```

Chains:

- `forward_prenat_account`: `type filter hook forward priority -150`; counts client traffic before source NAT.
- `gateway_forward`: `type filter hook forward priority 0`; isolated gateway allow rules.
- `wan_nat`: `type nat hook postrouting priority srcnat`; masquerades monitored LAN traffic to WAN.

The accounting chain is the only chain with byte counters. This avoids counting the same forwarded packet again in policy or NAT chains.

NAT rule:

```text
oifname "<WAN>" ip saddr @monitored_lan4 masquerade
```

Per-device attribution happens before NAT using the original client IP and the device resolver's MAC mapping from DHCP leases, neighbour table, and observed L2 data.

## DNS/DHCP Recommendation

Recommendation: Option C, dedicated gateway DHCP using dnsmasq on the monitored LAN, forwarding DNS to Pi-hole.

Reasoning:

- Pi-hole already owns host port 53 on all interfaces.
- Keeping Pi-hole as DNS preserves DNS log value for later correlation.
- A separate monitored-LAN DHCP instance keeps gateway lease ownership explicit and easier to rollback.
- The DHCP service must bind only to the new LAN interface and must not serve `192.168.1.0/24`.

Rejected for initial live deployment:

- Option A, Pi-hole DNS only with unrelated DHCP: workable, but gives weaker control over lease/device identity unless DHCP lease export is integrated carefully.
- Option B, Pi-hole DNS plus DHCP: technically possible, but Docker-published DNS and Pi-hole DHCP configuration increase conflict and rollback risk on this server.

No plan should run two DHCP servers on the monitored LAN.

## Persistence

Use NetworkManager because it currently owns `enp0s31f6` and `wlp1s0`.

Planned persistent components:

- NetworkManager connection for the new LAN interface with static `192.168.50.1/24`.
- sysctl drop-in for IPv4 forwarding.
- nftables rules loaded from a project-owned file containing only `inet network_monitor`.
- dedicated dnsmasq service bound to the monitored LAN interface.
- existing Docker services unchanged.
- network-monitor collector/API/web/db startup order unchanged.

## Rollback

Rollback must remove only project-owned gateway state:

```bash
nft delete table inet network_monitor
systemctl stop network-monitor-dnsmasq.service
ip addr del 192.168.50.1/24 dev <SECOND_INTERFACE>
sysctl -w net.ipv4.ip_forward=<previous-value>
```

Do not flush Docker rules. Do not stop Pi-hole. Do not modify `enp0s31f6`.

## Automatic Rollback Safety

Live apply should support a confirmation timer:

1. Save prior forwarding/interface/service state.
2. Apply gateway changes.
3. Start a 120-second rollback timer.
4. Operator confirms from the existing management LAN.
5. If not confirmed, rollback automatically.

This is implemented only as dry-run planning in this branch. Live apply remains disabled.

## Remaining Live Activation Blockers

- Add a dedicated second Ethernet interface.
- Install/validate host nftables tooling.
- Confirm candidate LAN interface name, MAC, link state, and speed after hardware is connected.
- Confirm Pi-hole DNS forwarding target for monitored LAN clients.
- Run `network-monitor-gateway status` and readiness after the adapter is connected.
- Obtain explicit operator approval for live apply.
